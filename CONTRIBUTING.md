# Contributing to OpenSWMM Gymnasium

Thank you for your interest in contributing to OpenSWMM Gymnasium. This document explains how to get started, the development workflow, and what we expect from contributions.

## Code of Conduct

All participants in this project are expected to follow our [Code of Conduct](CODE_OF_CONDUCT.md). Please read it before contributing.

## Contributor License Agreement

Before your first pull request can be merged you must sign the [CLA](CLA.md). Signing is automated via CLA Assistant on pull request open; see CLA §9 for the manual fallback.

## 1. Getting Started

### Prerequisites

- Python 3.10 or later
- Git
- The [openswmm.engine](https://github.com/HydroCouple/openswmm.engine) Python bindings installed (v6 handle-based, required by **all** tests — this package does not mock the engine)

### Development Setup

```bash
git clone https://github.com/HydroCouple/openswmm.gymnasium.git
cd openswmm.gymnasium
pip install -e ".[dev,docs]"
```

This installs the package in editable mode along with all development and documentation dependencies (gymnasium, pytest, ruff, sphinx, etc.).

## 2. Repository & Technical Management

The **Technical Manager** of openswmm.gymnasium is the maintainer of record responsible for accepting contributions, setting technical direction, and exercising the rights granted under the [CLA](CLA.md). The current Technical Manager is [@cbuahin](https://github.com/cbuahin).

The Technical Manager role may be transferred to a new maintainer by a public announcement on the project Discussions page and an update to this document and to [AUTHORS.md](AUTHORS.md). Rights granted under the [CLA](CLA.md) persist through any such transition.

## 4. Development Workflow

### Create a Branch

```bash
git checkout -b feature/your-feature-name
# or
git checkout -b fix/your-fix-description
```

### Make Your Changes

- Follow the existing code style (enforced by ruff)
- Add or update tests for any new or changed functionality
- Keep commits focused and atomic
- For environment-API changes, ensure the env still passes `gymnasium.utils.env_checker.check_env`

### Run Quality Checks

```bash
# Lint
ruff check src/ tests/

# Format
ruff format src/ tests/

# Unit tests (require the real openswmm.engine — no mocks)
pytest tests/unit/ -v

# Unit tests with coverage
pytest tests/unit/ --cov=openswmm_gymnasium --cov-report=term-missing

# Integration tests (also real engine, end-to-end scope)
pytest tests/integration/ -v

# Regression tests (golden trajectories against bundled benchmarks)
pytest tests/regression/ -v
```

All three tiers run against the real `openswmm.engine.Solver` driving
tiny in-tree `.inp` fixtures. The split is by **scope**
(single-component vs. end-to-end vs. golden trajectory), not by whether
the engine is real.

### Build Documentation

```bash
sphinx-build -b html docs docs/_build/html
```

### Submit a Pull Request

- Push your branch and open a pull request against `main`
- Provide a clear description of what your changes do and why
- Reference any related issues (e.g., "Fixes #42")
- Ensure CI checks pass and the CLA bot has recorded your signature

## 5. Project Structure

See [docs/IMPLEMENTATION_PLAN.md](docs/IMPLEMENTATION_PLAN.md) for the authoritative module layout. Summary:

```
src/openswmm_gymnasium/
    __init__.py            # Package version + gymnasium.register() calls
    envs/                  # SwmmEnv, SwmmMOEnv, scenario-specific subclasses
    spaces/                # Design (CIP) + runtime (RTC) action-space builders
    observations/          # Observation builders over Solver state
    rewards/               # Reward / objective registry (flooding, overflow, etc.)
    scoring/               # Multi-objective scoring (normalized hypervolume, IGD+)
    wrappers/              # Vector-reward, scalarization, action-mask wrappers
    benchmarks/            # Reference scenarios bundled with the package
    _engine/               # Thin adapter over openswmm.engine.Solver
    _util/                 # Internal helpers (validation, formatting)
tests/
    conftest.py            # Shared fixtures (per-test copy of in-tree INPs)
    data/                  # Tiny hand-authored INP fixtures (≤ 30 elements)
    unit/                  # Single-component tests against the real Solver
    integration/           # End-to-end tests against the real Solver
    regression/            # Golden-trajectory tests against bundled benchmarks
docs/
    getting-started/       # installation, configuration, quickstart
    user-guide/            # envs, action_spaces, observations, rewards, scoring
    developer/             # architecture, testing, contributing
    api/                   # autogenerated API reference
```

## 6. Conventions

### Code Style

- **Formatter/linter:** [Ruff](https://docs.astral.sh/ruff/) (configuration in `pyproject.toml`)
- **Target Python:** 3.10+
- **Type hints:** Use type annotations for all public function signatures
- **Docstrings:** **Epytext** convention (`@param`, `@type`, `@return`, `@rtype`, `@raise`, `@ivar`, `@author`, `@copyright`, `@license`). See plan §13 for the full tag table. Google-style, NumPy-style, and reST-field-list docstrings are not permitted.

### Testing

- All new envs, spaces, observations, rewards, and scoring methods must have corresponding unit tests
- **Do not mock `openswmm.engine`.** All tests drive the real handle-based `openswmm.engine.Solver` against tiny `.inp` fixtures in `tests/data/`. Mocked-engine PRs will be rejected at review.
- Scoring tests (`test_scoring_*`) are the only exception — pure math against closed-form references, no solver needed
- Use `pytest-asyncio` for async test functions (auto mode is configured)
- Test files follow the naming convention `test_<module>.py`
- New environments must pass `gymnasium.utils.env_checker.check_env`

### Environment Development

Each environment lives under `src/openswmm_gymnasium/envs/`. To add a new environment:

1. Subclass `SwmmEnv` (single-objective) or `SwmmMOEnv` (multi-objective)
2. Declare `action_space` and `observation_space` using factories from `spaces/` and `observations/`
3. Implement `reset()` and `step()` per the Gymnasium 1.x API (return `obs, reward, terminated, truncated, info`; MO returns vector reward)
4. Register the env in `src/openswmm_gymnasium/__init__.py` via `gymnasium.register`
5. Add a regression test that loads a small reference INP and asserts stable cumulative reward over a fixed seed

### Commit Messages

- Use clear, descriptive commit messages
- Start with a verb in imperative mood (e.g., "Add hypervolume scoring", "Fix solver close on env.reset")
- Reference issues where applicable

## 7. Reporting Issues

- Use [GitHub Issues](https://github.com/HydroCouple/openswmm.gymnasium/issues) to report bugs or request features
- Include steps to reproduce for bugs
- Include your Python version, OS, gymnasium version, and openswmm.engine version
